Microsoft Azure AZ-900 30 天全教材詳解

嚴謹釐清跨雲混淆、官方 Availability Zones 考點、Region Pairs 運作機制、SLA 條件與儲存體備援架構。

🎯 核心觀念釐清與避坑矩陣（避免以 AWS 思維誤套 Azure）

在備考 AZ-900 時，許多考生容易將其他雲端平台（如 AWS）的架構習慣直接套用，或將典型情境誤當成無例外的鐵律。以下彙整官方規範：

常見誤解與混淆 Microsoft Learn 官方正確架構 考試關鍵重點與答題原則
「Availability Zones 是 AWS 專屬，Azure 沒有 AZ」 不正確！Azure 具備 Availability Zones，且為 AZ-900 重要核心考點。支援的 Region 通常有 3 個獨立 AZ。 AZ 提供資料中心級別容錯（獨立電力、冷卻與網路）。但請注意：並非所有 Azure Region 都有 AZ，不同服務或 SKU 的支援狀態也不同。
「Region Pairs 距離固定至少 300 英哩，且自動完成全系統 DR」 不準確！微軟在設計多數 Region Pairs 時以相距約 300 英哩為設計目標，但並非全無例外之固定鐵律；且配對絕不會自動替所有資源完成災難復原。 Region Pairs 提供：循序滾動更新、大規模事故優先循序復原，以及特定服務（如 GRS）預設異步複寫。但應用層 DR 與 VM 容錯移轉必須由使用者自行設計規劃。
「只要跨 Availability Zones 部署，就無條件保證 99.99% SLA」 需滿足前提！需在支援 AZ 的 Region、支援的 VM SKU，並在 2 個或以上 AZ 各部署至少 1 個 VM，才符合微軟 99.99% 連線 SLA 條件。 單一 VM (Premium SSD) = 99.9%；Availability Set = 99.95%；符合資格的跨 AZ 部署 = 99.99%。考試時不能將固定 zones 部署視為任意區域任意 SKU 的萬靈丹。
「RA-GRS 代表主要區域有跨可用性區域 (AZ) 備援」 混淆！RA-GRS 的主要區域採用 LRS（單一資料中心 3 份副本）。主要區域跨 3 個 AZ 的是 RA-GZRS。 記憶口訣：帶 Z 的（ZRS / GZRS / RA-GZRS）主要區域才跨 3 個 AZ；單純 GRS / RA-GRS 主要區域只有單一資料中心 LRS 備援。
「Azure 會自動將客戶資料跨國備援至其他國家」 違背資料主權原則！Azure 保證預設情況下，資料只會在同一個 Geography（地理邊界） 內進行複寫與備援，不會未經授權跨國傳送。 Geography 定義資料駐留（Data Residency）與法規遵循邊界（例如 Asia Pacific 內的 East Asia 與 Southeast Asia 配對）。

DAY 1

雲端概念、雲端模型與責任共擔模型 (Shared Responsibility)

Domain 1: 描述雲端概念 (25–30%)

📌 核心知識架構

  • 雲端服務類型比較：
    • IaaS (基礎結構即服務)：客戶管理 OS、中介軟體、Runtime、應用程式、資料。雲端商只負責實體伺服器、網路與虛擬化（如 Azure VM）。最具彈性、控制權最大。
    • PaaS (平台即服務)：客戶只需負責應用程式與資料，OS 更新與修補由微軟全權管理（如 Azure App Service、Azure SQL Database）。
    • SaaS (軟體即服務)：使用者只需關注端點使用與身分存取，其餘所有底層由供應商提供（如 Microsoft 365）。
  • 責任共擔模型：無論在任何模型中，資訊與資料（Data）、身分識別與目錄（Identity）、使用者端裝置（Endpoints）永遠由客戶負擔最終管理責任！
  • 財務模型：CapEx（資本支出，需前期大量購買硬體設備並攤提折舊）vs OpEx（營運支出，依用量隨用隨付 Consumption-based，無預付費用，敏捷彈性）。
經典實戰試題：責任共擔模型邊界
  • 題目：某公司正將其在地端執行的自建虛擬機器遷移至 Azure IaaS 虛擬機器。在此架構下，誰負責為虛擬機器中的客體作業系統 (Guest OS) 安裝安全性更新修補程式？
  • A. Microsoft
  • B. 客戶（使用者自身）
  • C. 伺服器硬體廠商
  • D. 雙方平分責任
✓ 正確答案：B
詳解：在 IaaS 模型中，Microsoft 僅負責維護實體主機 (Hypervisor) 與底層基礎架構；客體作業系統 (Guest OS) 的更新、防毒軟體與系統配置完全屬於客戶的責任。

DAY 2

Azure 基礎架構全解析：Region, AZ, Region Pairs 與 SLA

Domain 2: 描述 Azure 架構與服務 (35–40%)

📌 核心知識架構與避坑指南

  • Azure Region（區域）：由一個或多個透過低延遲專用網路互聯的資料中心群所組成的地理範疇。
  • Availability Zones（可用性區域）：
    • 一個 Region 內實體隔離的資料中心，擁有獨立的電力 (Power)、冷卻 (Cooling) 與網路 (Networking)。
    • 考點修正：AZ 亦為 Azure 核心功能（並非 AWS 獨有）。支援 AZ 的區域通常提供至少 3 個獨立可用性區域。
    • 防護範圍：AZ 能抵禦「單一整座資料中心」完全故障。
  • Region Pairs（區域配對）：
    • 每個 Azure 區域會在同一 Geography 內與另一個區域配對（例如 East Asia 配對 Southeast Asia）。
    • 機制優勢：(1) 循序滾動更新（微軟絕不會同時更新配對中的兩個區域）；(2) 大規模天災時優先復原其中一個區域；(3) GRS 預設複製至配對區域。
    • 重要觀念：配對距離設計目標通常約 300 英哩，但並非全無例外之絕對鐵律；且配對不會自動替應用程式接管故障，應用層 DR 需自行規劃。
  • SLA 保證條件：
    • 單一 VM（搭配 Premium SSD）：SLA 為 99.9%
    • 同一資料中心 Availability Set：SLA 為 99.95%
    • 跨 Availability Zones 部署（至少 2 個 VM 分散於 2 個 AZ，且符合 SKU/Region 支援）：SLA 為 99.99%
經典實戰試題：Region Pairs 與更新行為
  • 題目：關於 Azure Region Pairs 的特性，下列哪一項敘述是正確的？
  • A. 當微軟進行計畫性平台更新時，會同時在配對的兩個區域部署更新以節省維護時間
  • B. 當發生波及多個區域的廣泛重大災害時，Azure 會確保所有配對組中至少有一個區域獲得優先復原處理
  • C. 啟用配對後，所有在主要區域建立的 VM 都會無條件自動在次要區域即時鏡像備份
  • D. 使用者可以隨時在 Azure 入口網站中自由更改區域配對對象
✓ 正確答案：B
詳解：Region Pairs 採用「循序更新 (Sequenced Updates)」，絕不會同時更新兩者（A 錯）；配對不會自動替所有 VM 做應用層鏡像切換（C 錯）；配對關係為 Azure 底層預先定義固定，客戶無法自行變更（D 錯）。

DAY 3

Sovereign Clouds 主權雲與合規性 (Azure Government & China)

Domain 3: 描述 Azure 管理與治理 (30–35%)

📌 核心知識架構

  • Azure Government (美國政府雲)：專為美國聯邦、州、地方政府及其合約承包商打造，實體與邏輯上完全隔離於全球 Azure 公有雲，員工需通過美國背景篩選。
  • Azure China (世紀互聯營運)：根據中國法規要求，由第三方本地公司「世紀互聯 (21Vianet)」獨立營運與維護，與全球公有雲完全物理隔離。
  • Microsoft Purview & Compliance Manager：協助組織持續追蹤法規標準（如 ISO 27001、GDPR、HIPAA），提供合規分數與改善建議。
經典實戰試題：主權雲隔離特性
  • 題目：某美國國防承包商需要部署處理嚴格受控非機密資訊 (CUI) 的系統。哪種 Azure 雲端環境能夠滿足其專屬的實體隔離與嚴格法規遵循需求？
  • A. Azure Public Cloud（一般全球公有雲）
  • B. Azure Government（美國主權政府雲）
  • C. 僅能在內部私有資料中心執行，不可使用任何雲端
  • D. Azure Commercial Cloud 配合隨選 VPN
✓ 正確答案：B
詳解：Azure Government 是專為美國政府機構及其供應商設立的主權獨立雲端實例，與一般公有雲完全實體與網路隔離。

DAY 4

Azure 管理工具選型：Portal, CLI, PowerShell, Cloud Shell, Arc

Domain 3: 描述 Azure 管理與治理 (30–35%)

📌 核心知識架構

  • Azure Portal：基於網頁瀏覽器的圖形化介面 (GUI)，適合初學者、視覺化監控與單一資源手動配置。
  • Azure CLI：跨平台命令列工具（Windows, macOS, Linux），語法以 az 開頭（例如 az group create），特別適合 Bash 腳本。
  • Azure PowerShell：基於 PowerShell 的模組，語法採用「動詞-名詞」格式（例如 New-AzResourceGroup）。
  • Azure Cloud Shell：直接在瀏覽器中執行的互動式終端機，免本機安裝，自動驗證身分，可自由切換 Bash 或 PowerShell。
  • Azure Arc：將 Azure Resource Manager (ARM) 管理平面的治理與安全能力，延伸至地端資料中心、邊緣裝置或其他公有雲 (AWS/GCP)！
經典實戰試題：管理工具跨雲延伸
  • 題目：某企業在地端機房擁有數百台 Windows 與 Linux 伺服器，同時在 AWS 上也有 VM。管理者希望使用 Azure Policy 和 Azure Monitor 來「統一管理」所有平台上的伺服器。應使用哪項服務？
  • A. Azure DevOps
  • B. Azure Arc
  • C. Azure Migrate
  • D. Azure Traffic Manager
✓ 正確答案：B
詳解：Azure Arc 能簡化跨環境治理，將地端伺服器、Kubernetes 叢集與多雲資源投影成 Azure 中的資源，以套用 Azure 原生原則與合規設定。

DAY 5

基礎架構即程式碼 (IaC)：ARM Templates 與 Bicep

Domain 3: 描述 Azure 管理與治理 (30–35%)

📌 核心知識架構

  • 宣告式語法 (Declarative Syntax)：「宣告結果，而非定義步驟」。告訴 Azure「我需要什麼狀態」，系統自動推算相依性並完成佈建。
  • 冪等性 (Idempotency)：重複執行相同範本多次，只要設定未變，結果保持一致且不會造成資源重複建立或損毀。
  • ARM Templates (JSON)：傳統標準宣告式範本，但 JSON 括號複雜且缺乏型別安全檢查。
  • Bicep：微軟官方開發的 Azure 原生領域特定語言 (DSL)，語法簡潔乾淨、支援模組化與 VS Code 程式碼自動完成，編譯後會自動轉換為 ARM JSON 執行。
經典實戰試題：宣告式 IaC 工具
  • 題目：團隊需要一種微軟原生推薦的基礎架構即程式碼 (IaC) 語言，具有比 JSON 範本更簡潔易讀的語法，且能保證重複部署的一致性（冪等性）。應選擇？
  • A. Azure Bicep
  • B. Azure Automation Runbooks
  • C. PowerShell DSC 手動腳本
  • D. Azure Logic Apps
✓ 正確答案：A
詳解：Bicep 是微軟原生設計的宣告式 IaC 語言，直接編譯成 ARM 範本，提供簡潔語法與宣告式冪等性保證。

DAY 6

監控與健全狀況：Azure Advisor 與 Azure Service Health

Domain 3: 描述 Azure 管理與治理 (30–35%)

📌 核心知識架構

  • Azure Advisor (顧問)：分析資源設定與遙測數據，依據五大主軸提供個人化最佳做法建議：成本 (Cost)、安全性 (Security)、可靠性 (Reliability)、效能 (Performance)、卓越營運 (Operational Excellence)。
  • Azure Service Health (服務健全狀況)：包含三大視圖：
    • Azure Status (全局狀態)：全網頁公開檢視所有 Azure 服務的宏觀運作狀態。
    • Service Health (服務健康狀態)：針對「您目前訂用帳戶中所使用到的服務與區域」進行個人化影響通知。
    • Resource Health (資源健康狀態)：針對「特定單一資源實例」（如某台特定 VM）診斷是否正常運行。
經典實戰試題：服務中斷通知工具選型
  • 題目：Azure 某個區域發生網路光纖切斷事故，影響了您訂用帳戶中的部分虛擬機器。應使用哪項服務來獲取「專門針對您受影響資源」的最新官方事件報告與 RCA 根本原因分析？
  • A. Azure Monitor
  • B. Azure Service Health
  • C. Azure Advisor
  • D. Azure Security Center
✓ 正確答案：B
詳解：Azure Service Health 提供客製化的健康儀表板，專注於您的特定訂用帳戶資源是否遭受微軟基礎設施事件影響，並提供後續修正報告。

DAY 7

階段總複習①：核心架構與治理觀念整合檢驗

綜合階段評量 (Domain 1 & 3)

📌 核心觀念統整回顧

完成第一週基礎後，請確保能熟練回答下列核心心智圖分支：

  • CapEx vs OpEx：地端購買伺服器為 CapEx；Azure 隨用隨付、無預付費用為 OpEx。
  • 彈性 (Elasticity) vs 可調整延展性 (Scalability)：水平擴充 (Scale-out) 加機器；垂直調整 (Scale-up) 升級 CPU/RAM；彈性是指系統能夠依即時負載「自動放大與縮小」。
  • 敏捷性 (Agility)：幾分鐘內即可快速佈建或銷毀資源，大幅縮短上市時間。
  • 災難復原 (Disaster Recovery)：專注於毀滅性災害後快速恢復資料與應用（RTO / RPO）。

DAY 8

運算服務：虛擬機器 VM、VMSS 與可用性機制

Domain 2: 描述 Azure 架構與服務 (35–40%)

📌 核心知識架構

  • Azure Virtual Machines (VM)：IaaS 代表性服務，完整控制作業系統，適用自訂軟體與直接遷移 (Lift-and-Shift)。
  • Virtual Machine Scale Sets (VMSS)：部署與管理一組完全相同的負載平衡 VM，支援排程或計量指標（如 CPU 75%）自動水平縮放 (Autoscale)。
  • Availability Set (可用性設定組)：
    • 在「同一資料中心內」分散實體機架：Fault Domain (容錯網域，隔離電源與交換器) 與 Update Domain (更新網域，隔離微軟維護重開機)。
    • SLA 保證為 99.95%。
  • 跨 Availability Zones 部署：
    • 將 VMSS 或個別 VM 分散部署於多個 AZ，抵禦整個資料中心層級故障。
    • 符合條件下 SLA 可達 99.99%（注意：需為支援 AZ 的區域與支援的 SKU，且在 2 個或以上 AZ 各部署至少 1 台 VM）。
  • Spot Virtual Machines：以極高折扣（最高達 90%）租借 Azure 閒置運算容量，但當 Azure 需要資源時會隨時收回中斷，無可用性 SLA 保證，僅適合中斷不影響結果的批次運算。
經典實戰試題：自動水平伸縮服務選型
  • 題目：某電商網站預期在促銷期間流量暴增，希望在 CPU 使用率超過 80% 時自動增加伺服器實體，在流量降溫時自動減少機器以降低成本。最合適的服務是？
  • A. Azure App Service 靜態方案
  • B. Azure Virtual Machine Scale Sets (VMSS)
  • C. 單一可用性設定組內的固定 5 台 VM
  • D. Azure Dedicated Host
✓ 正確答案：B
詳解：VMSS 專為相同 VM 的自動水平彈性伸縮 (Autoscale) 設計，能根據計量規則動態增減實例數量。

DAY 9

應用程式服務：Azure App Service 與 Serverless Functions

Domain 2: 描述 Azure 架構與服務 (35–40%)

📌 核心知識架構

  • Azure App Service (PaaS)：完全受管的 Web 應用程式、RESTful API 與行動後端託管平台。支援 .NET, Java, Node.js, Python 等，提供自動延展、SSL 憑證管理與部署位置 (Deployment Slots)。
  • Azure Functions (無伺服器 Serverless)：
    • 事件驅動 (Event-driven)：當事件發生時（如 HTTP 請求、佇列訊息到達、檔案上傳）才觸發執行程式碼區塊。
    • 依執行次數計費：在 Consumption 方案下，只有程式碼實際執行時才計費，閒置時完全零費用。
  • Azure Logic Apps (無伺服器整合)：低程式碼/無程式碼 (Low-code/No-code) 工作流程編排工具，提供數百個現成連接器整合 SaaS 與地端系統。
經典實戰試題：事件驅動無伺服器程式碼
  • 題目：開發人員需要編寫一段簡短的程式碼，每當有新圖片上傳到 Azure Storage 時，自動縮小圖片尺寸，且希望「無任何圖片上傳時不需要支付任何伺服器費用」。應選用？
  • A. Azure Virtual Machines
  • B. Azure Functions (Consumption Plan)
  • C. Azure Container Instances
  • D. Azure App Service 獨立方案
✓ 正確答案：B
詳解：Azure Functions 專為事件驅動程式碼設計，搭配 Consumption 方案可在無任務時完全不產生成本。

DAY 10

容器服務：Azure Container Instances (ACI) 與 AKS

Domain 2: 描述 Azure 架構與服務 (35–40%)

📌 核心知識架構

  • 容器 vs 虛擬機器：VM 虛擬化整套硬體並包含獨立 Guest OS（較重）；容器共用主機 OS 核心，僅封裝應用程式與相依函式庫（輕量、秒級啟動）。
  • Azure Container Instances (ACI)：最快速、最簡單在 Azure 執行單一容器的方式。無伺服器容器，免管理任何 VM，免配置 Kubernetes 叢集，按秒計費。
  • Azure Kubernetes Service (AKS)：完全受管的企業級容器協調與編排 (Orchestration) 平台。適合複雜微服務架構、多容器服務發現、自我修復與自動負載平衡。微軟免費提供叢集主控節點 (Control Plane)。
經典實戰試題：ACI vs AKS 適用情境
  • 題目：團隊需要執行一個短暫的資料處理容器任務，每天僅執行一次，執行時間約 5 分鐘，且團隊不想設定與管理任何 Kubernetes 叢集。最理想的服務是？
  • A. Azure Kubernetes Service (AKS)
  • B. Azure Container Instances (ACI)
  • C. Azure App Service 專用叢集
  • D. Azure Virtual Machine Scale Sets
✓ 正確答案：B
詳解：ACI 支援無需管理伺服器或容器編排平台的按需即開即用容器執行環境，非常適合短期隔離任務。

DAY 11

網路架構：Azure Virtual Network (VNet) 與 Subnet

Domain 2: 描述 Azure 架構與服務

📌 核心重點

  • VNet (虛擬網路)：Azure 私有網路隔離邊界。提供專屬 RFC 1918 私有 IP 位址區段。
  • Subnet (子網路)：將 VNet 劃分成更小的邏輯區段（例如 Web Subnet, DB Subnet），每個子網內保留 5 個 IP 供 Azure 內部使用。
  • VNet Peering (虛擬網路對等互連)：透過微軟高速骨幹私有網路直接串聯兩個 VNet（支援跨區域 Global VNet Peering），完全不走公共網際網路，延遲極低。
DAY 12

網路安全：網路安全群組 (NSG) 與應用程式安全性群組 (ASG)

Domain 2: 描述 Azure 架構與服務

📌 核心重點

  • NSG (Network Security Group)：第 4 層 (L4) 封包過濾防火牆，依來源/目的地 IP、連接埠與通訊協定控制流量。
  • 規則優先順序：範圍為 100 至 4096，數值越小優先權越高，只要符合第一條規則即停止比對。
  • ASG (Application Security Group)：將具有相同角色的虛擬機器（例如 Web 伺服器）分組，讓 NSG 規則可直接指定 ASG 標籤，免維護龐大 IP 清單。
DAY 13

混合雲網路連線：VPN Gateway vs Azure ExpressRoute

Domain 2: 描述 Azure 架構與服務

📌 核心重點

  • VPN Gateway (站對站 VPN)：透過「公共網際網路」建立加密的 IPsec/IKE 通道，成本較低，但速度與延遲受公網流量影響。
  • Azure ExpressRoute：透過電信服務商建立「專屬私有連線」，完全不經過公共網際網路！具備極高可靠性、最高頻寬與最低延遲，適合大型企業與金融核心。
DAY 14

負載平衡器選型：Azure Load Balancer vs Application Gateway

Domain 2: 描述 Azure 架構與服務

📌 核心重點

  • Azure Load Balancer (第 4 層 L4)：傳輸層負載平衡器，僅根據 IP 與 TCP/UDP Port 轉發流量，極低延遲、超高輸送量。
  • Application Gateway (第 7 層 L7)：應用層負載平衡器，支援 Cookie 關聯、URL 路徑路由（如 /images 轉發不同叢集）、SSL 終止 (SSL Offloading)，並可啟用 Web 應用程式防火牆 (WAF) 防禦 SQL Injection 與 XSS！
DAY 15

儲存體：Azure Blob Storage 與存取層級 (Tiers)

Domain 2: 描述 Azure 架構與服務

📌 核心重點

  • Hot Tier (常用層)：儲存成本最高，但存取 (讀寫) 費用最低。適合經常存取資料。
  • Cool Tier (非常用層)：儲存成本較低，存取費用較高。適合存放至少 30 天且不常讀取的資料。
  • Cold Tier (冷層)：介於 Cool 與 Archive 之間，存放至少 90 天。
  • Archive Tier (封存層)：儲存費用極低，但處於離線狀態，存取費用最高且讀取前需耗費數小時解凍 (Rehydrate)。適合法規保存數年之備份。
  • 生命週期管理 (Lifecycle Management)：自動化規則，依據最後修改時間自動將 Blob 由 Hot 轉 Cool 轉 Archive 甚至刪除。
DAY 16

Azure Files 與受控磁碟 (Managed Disks)

Domain 2: 描述 Azure 架構與服務

📌 核心重點

  • Azure Files：完全受管的雲端檔案共用服務，支援業界標準 SMB 與 NFS 通訊協定，可同時掛載至 Windows、macOS 與 Linux。
  • Managed Disks (受控磁碟)：微軟負責管理磁碟底層儲存硬體。分為：
    • Standard HDD：最低成本，適合備份與非關鍵應用。
    • Standard SSD：具性價比的輕量工作負載。
    • Premium SSD：高效能與低延遲，生產環境與資料庫首選。
    • Ultra Disk：微軟頂級磁碟，支援亞毫秒延遲與超高 IOPS，適合重量級 SAP HANA 等交易資料庫。

角色型存取控制 (RBAC) 與階層管理

資安架構：零信任 (Zero Trust) 與 Microsoft Defender for Cloud

Domain 3: 描述 Azure 管理與治理

DAY 30

終局戰：儲存體備援 (Redundancy) 與高可用性 SLA 終極彙整

全域統整篇

📌 儲存體備援完整對照表（必考題關鍵點）

備援選項 主要區域複寫方式 次要區域複寫方式 容錯防護層級
LRS (本地備援) 同一資料中心內同步儲存 3 份副本 無跨區複製 防範磁碟與機架故障（無法承受整座資料中心損毀）
ZRS (可用性區域備援) 跨 3 個 Availability Zones 同步複寫 無跨區複製 防範單一整座資料中心完全中斷火災
GRS (異地備援) 主要區域採 LRS (單一資料中心 3 份) 非同步複寫至數百英哩外次要配對區域 (次要區域採 LRS) 防範重大區域性災難（但次要區域平時無法讀取，需容錯移轉後才可讀寫）
RA-GRS (讀取存取異地備援) 主要區域採 LRS (單一資料中心 3 份) 非同步複寫至次要區域，且次要端點隨時提供唯讀存取 主區域掛掉時，可立即從次要區域持續讀取資料
GZRS (異地區域備援) 主要區域採 ZRS (跨 3 個 AZ 同步複寫) 非同步複寫至次要配對區域 (次要區域採 LRS) 兼具主區域 AZ 容錯 + 跨區域災難復原最高等級保護
RA-GZRS 主要區域採 ZRS (跨 3 個 AZ 同步複寫) 非同步複寫至次要區域，且次要端點隨時提供唯讀存取 最高等級儲存體耐用性與業務連續性
經典實戰試題：RA-GRS vs RA-GZRS 觀念區分
  • 題目：某商業銀行的核心存檔合規要求：資料在主要區域必須跨三個實體隔離的可用性區域 (AZ) 同步複製，同時還必須非同步複製到配對次要區域，且次要區域必須能即時提供唯讀查詢。應選擇何種備援方案？
  • A. Locally redundant storage (LRS)
  • B. Read-access geo-redundant storage (RA-GRS)
  • C. Read-access geo-zone-redundant storage (RA-GZRS)
  • D. Zone-redundant storage (ZRS)
✓ 正確答案：C
詳解：RA-GZRS 結合了 ZRS（主要區域跨 3 個 AZ）與異地複寫及次要端點唯讀存取。RA-GRS 的主要區域只有 LRS，無法抵抗整座資料中心故障。
